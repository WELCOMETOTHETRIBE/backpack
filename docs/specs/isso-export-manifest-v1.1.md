# ISSO Export Manifest — v1.1 Specification

**Status:** Draft, under build (Sprint 0–6 plan, see end of doc).
**Owners:** Codex (Trust Codex / control-plane) · EnclaveWatch (vault agent).
**Replaces / extends:** v1.0 (`/api/enclavewatch/weekly-review/ingest`). v1.0 stays live during transition.

---

## 1. Why this exists

Today, evidence freshness on the codex relies on a patchwork of cadenced attestations — one form per control, one signature per cycle. That model scales badly and concentrates the evidence story in attestations the C3PAO already discounts as "self-reported."

The ISSO weekly review IS the human-judgment moment that an assessor wants to see. Today it touches one register (`audit_log_review`). v1.1 makes it the structured, signed refresh mechanism for **every register that benefits from ISSO oversight**, plus a one-shot `control_freshness` block that explicitly affirms which controls were observed operating in the review window.

**Net effect:** one signed weekly export refreshes evidence for ~25 controls and lets us retire cadenced per-control attestations on operational lanes (audit, maintenance, incident, access review, vuln remediation, etc.). Attestations remain only for architectural facts the ISSO can't observe weekly (e.g., 3.13.13 mobile-code policy).

---

## 2. Versioning + transport

- **Endpoint (v1.1):** `POST /api/enclavewatch/isso-export/ingest`
- **Endpoint (v1.0, retained):** `POST /api/enclavewatch/weekly-review/ingest` — continues to accept v1.0 manifests until EnclaveWatch is fully migrated. v1.0 ingests a strict subset of v1.1.
- **Auth:** EnclaveWatch bearer token (existing `organizations.enclavewatch_api_token`). No new credential.
- **Content-Type:** `application/json; charset=utf-8`
- **Signing:** HMAC-SHA256 over `method + path + Date header + body`, shared secret in vault `appsettings`. Reject requests with `Date` skew > 60s. Idempotency via `manifest_id` (UUID generated by EnclaveWatch).
- **Forbidden keys (rejected at ingest):** `raw_event_xml`, `raw_event_body`, `command_line`, `raw_command_line`, `password`, `secret`, `private_key` — same denylist as v1.0. Raw logs stay on the vault per boundary rules.

## 3. Manifest body shape

```json
{
  "manifest_version": "1.1",
  "manifest_id": "uuid-v4",
  "acknowledgement": {
    "vault_id": "string",
    "customer_id": "uuid",
    "review_period_start": "RFC3339",
    "review_period_end": "RFC3339",
    "review_result": "clean | findings | blocked",
    "raw_logs_retained_on_vault": true,
    "event_count": 0,
    "evidence_bundle_hash": "sha256:...",
    "weekly_manifest_hash": "sha256:...",
    "signatory": { "name": "string", "role": "ISSO|alt", "signed_at": "RFC3339" },
    "export_signature": "base64(HMAC-SHA256(...))"
  },
  "review_summary": {
    "controls_touched": ["3.1.7", "3.3.2", "3.3.3", "3.7.1", "..."],
    "events_reviewed_count": 0,
    "anomalies_count": 0,
    "notes": "string (≤ 4000 chars, no raw events)"
  },
  "registers": {
    "audit_log_review":      { "weekly_review": { /* see §4.1 */ } },
    "maintenance_log":       {
      "break_glass_signins":   [ /* §4.2 */ ],
      "scheduled_maintenance": [ /* §4.3 */ ],
      "remote_maintenance":    [ /* §4.4 */ ]
    },
    "incident_log":          { "incidents_during_period": [ /* §4.5 */ ] },
    "access_authorizations": { "weekly_review_findings": [ /* §4.6 */ ] },
    "vuln_remediation":      { "verifications": [ /* §4.7 */ ] },
    "training_completion":   { "expiring_attestations": [ /* §4.8 */ ] },
    "policy_review":         { "stale_documents": [ /* §4.9 */ ] },
    "assessment_findings":   { "review_observations": [ /* §4.10 */ ] }
  },
  "control_freshness": {
    "freshly_observed_implemented": ["3.1.7", "3.3.2", "..."],
    "needing_attention": [ { "control_id": "3.7.5", "reason": "no maintenance activity in 90d", "severity": "warning" } ]
  },
  "previous_period_acknowledgments_review": {
    /* Closes the loop: ISSO confirms admin acknowledgments from prior period. See §5. */
    "items": [
      { "alert_id": "bg-...", "outcome": "verified_timely | overdue_escalated | dispute_pending", "isso_note": "string" }
    ]
  }
}
```

**Top-level keys are required**; section content is optional (an empty `registers.maintenance_log` is valid — means "no maintenance activity this period"). Empty section IS evidence (proves the watcher ran and saw nothing).

## 4. Per-register section schemas

### 4.1 `audit_log_review.weekly_review`

Mirror of v1.0. Writes a `governance_register_entries` row on `audit_log_review` register, `entry_type=weekly_review`, idempotent on `review_period_end`. Required fields: `review_period_start`, `review_period_end`, `reviewed_at`, `reviewed_by`, `summary`, `findings`. Provenance fields preserved: `enclavewatch_run_id`, `vault_id`, `evidence_bundle_hash`, `weekly_manifest_hash`.

**Backs:** 3.1.7, 3.3.2, 3.3.3, 3.3.5, 3.12.3, 3.14.3, 3.14.7

### 4.2 `maintenance_log.break_glass_signins[]`

Each item:
```json
{
  "alert_id": "bg-2026-05-04T08:42:13Z",
  "detected_at": "RFC3339",
  "source": "azure | vault",
  "upn": "emergency-bg-cui@MacTechSolutions256.onmicrosoft.com",
  "client_ip": "string",
  "app_or_resource": "string",
  "duration_seconds": 0,
  "session_correlation_id": "string",
  "actions_observed": ["string"],
  "ip_classification": "private | corp | unknown_or_shared"
}
```

Codex ingest: writes `maintenance_log` entry, `entry_type=break_glass_acknowledgment`, **`status=draft`**. Idempotent on `alert_id`. Surfaces in Monitoring tab card (Sprint 6). Admin completes acknowledgment form to finalize.

**New entry type added to `maintenance_log` schema:**
```json
{
  "type": "break_glass_acknowledgment",
  "required": ["alert_id","upn","detected_at","source","acknowledged_by","purpose_of_session","actions_taken","affected_systems","before_state","after_state","signed_at"],
  "optional": ["client_ip","duration_seconds","session_correlation_id","actions_observed","ip_classification","ticket","notes"],
  "enums": { "source": ["azure","vault"], "ip_classification": ["private","corp","unknown_or_shared"] }
}
```

**Lifecycle:** detected (draft) → admin signs (final) → ISSO verifies in next export's `previous_period_acknowledgments_review` block. If admin doesn't sign within 72h, codex emits `enclavewatch.break_glass.escalation_unjustified` audit event.

**Backs:** 3.1.7, 3.7.1, 3.7.2, 3.7.5

### 4.3 `maintenance_log.scheduled_maintenance[]`

Pre-planned admin actions. Mirrors existing `scheduled_maintenance` schema. ISSO observes during review window.

**Backs:** 3.7.1, 3.7.2

### 4.4 `maintenance_log.remote_maintenance[]`

Remote sessions (RDP/SSH/Bastion) observed during review window.

**Backs:** 3.7.5

### 4.5 `incident_log.incidents_during_period[]`

Items: `incident_id, opened_at, severity, summary, response_actions, closed_at?, ticket?`. Idempotent on `incident_id`. ISSO confirms each incident has a corresponding response.

**Backs:** 3.6.1, 3.6.2

### 4.6 `access_authorizations.weekly_review_findings[]`

ISSO's review of the access_authorization register itself: spotted anomalies, dormant accounts, unjustified grants. Each item: `subject_user, finding_type, severity, recommended_action`.

**Backs:** 3.1.5, 3.1.6, 3.5.1, 3.10.6

### 4.7 `vuln_remediation.verifications[]`

ISSO confirms verification status of vuln findings. Each item: `vuln_id, asset, status_observed (remediated|in_progress|risk_accepted), notes`.

**Backs:** 3.4.4, 3.11.2, 3.11.3, 3.14.1

### 4.8 `training_completion.expiring_attestations[]`

ISSO surfaces attestations approaching expiry. Each item: `subject_user, training_topic, expires_at, days_until_expiry`. Drives admin reminder workflow.

**Backs:** 3.2.1, 3.2.2, 3.2.3

### 4.9 `policy_review.stale_documents[]`

Each item: `doc_code, last_reviewed_at, days_since_review, recommended_action`. Drives policy review workflow.

**Backs:** 3.12.4

### 4.10 `assessment_findings.review_observations[]`

Each item: `observation_id, control_id, finding_type, severity, summary, recommended_action`. Drives mock-assessment + readiness workflow.

**Backs:** 3.12.1

## 5. `previous_period_acknowledgments_review` (closes the break-glass loop)

Each weekly export references the PRIOR period's break-glass alerts and reports outcome:

```json
{
  "items": [
    { "alert_id": "bg-...", "outcome": "verified_timely",      "isso_note": "Admin filed acknowledgment within 4h. Justification consistent with observed actions." },
    { "alert_id": "bg-...", "outcome": "overdue_escalated",    "isso_note": "No acknowledgment 96h after detection. Escalated to security@..." },
    { "alert_id": "bg-...", "outcome": "dispute_pending",      "isso_note": "Admin disputes session attribution. Investigation open as INC-..." }
  ]
}
```

Codex ingest: looks up the `maintenance_log.break_glass_acknowledgment` entry by `alert_id`, updates its status:
- `verified_timely` → entry final + `isso_verified_at` set + audit event `enclavewatch.break_glass.ack_verified`
- `overdue_escalated` → entry final + flagged + audit event `enclavewatch.break_glass.escalated`
- `dispute_pending` → entry remains open, links to incident_log entry

This is the closed loop. No alert can stay open indefinitely — every alert has a definitive outcome within two weekly cycles.

## 6. `control_freshness` (replaces cadenced attestations)

**`freshly_observed_implemented[]`:** ISSO explicitly affirms these controls were observed operating during the review window. The signed export IS the attestation. Codex ingest:
- For each control_id, sets `control_records.last_evaluated_at = export.review_period_end`
- Touches `control_records.updated_at`
- Logs audit event `enclavewatch.control.freshly_observed` per control

This means: instead of 25 separate cadenced attestations, the C3PAO sees 52 weekly signed exports, each affirming a list of controls — a much stronger evidence story.

**`needing_attention[]`:** ISSO surfaces controls where evidence is going stale. Each item maps to an admin workflow item in the codex (assigned to the control owner, surfaced on dashboard).

## 7. Idempotency + replay safety

- **manifest_id** is the top-level idempotency key. Re-ingesting the same `manifest_id` is a no-op (returns 200 with `{ replayed: true }`).
- **Per-section idempotency** uses the natural key documented above (alert_id, incident_id, vuln_id, period_end, etc.).
- HMAC + Date skew prevents replay attacks beyond 60s.
- Re-ingesting the SAME `manifest_id` with DIFFERENT body content is rejected (manifest_id must be a function of body content, not random — recommend `hash(body)` as manifest_id).

---

## 8. Backward compatibility

- v1.0 endpoint `/api/enclavewatch/weekly-review/ingest` continues to accept v1.0 manifests (no `manifest_version` field, or `manifest_version=1.0`).
- v1.0 ingestion routes through the SAME dispatcher as v1.1, treating the v1.0 body as a v1.1 manifest with only the `audit_log_review` section populated.
- EnclaveWatch can migrate gradually: ship v1.1 to one endpoint, both work, eventually retire v1.0 on a flag day.

## 9. Codex side: dispatcher architecture

```
POST /api/enclavewatch/isso-export/ingest
  → validateAuth(bearer)
  → validateSignature(HMAC, Date skew)
  → validateNoForbiddenKeys(body)
  → dedupeByManifestId(body.manifest_id)  // returns early if replay
  → for section in body.registers:
      registerHandlers[section](orgId, vaultId, body[section])
  → freshnessHandler(orgId, body.control_freshness)
  → ackReviewHandler(orgId, body.previous_period_acknowledgments_review)
  → emitAuditEvent('enclavewatch.isso_export.ingested', { manifest_id, controls_touched })
  → recompute affected control_records
  → return { ok: true, manifest_id, sections_processed, controls_touched }
```

Handler interface (one per register type):

```ts
type RegisterHandler = (ctx: IngestContext, payload: unknown) => Promise<HandlerResult>;
type HandlerResult = {
  entries_inserted: number;
  entries_updated: number;
  controls_touched: string[];
  warnings: string[];
};
```

This isolates per-register logic, makes adding new sections additive only, and gives a uniform telemetry surface.

## 11. Open questions (resolve before Sprint 1)

1. **Schema location for new `break_glass_acknowledgment` type:** add to `register_entry_schemas.v1.json` or bump to `register_entry_schemas.v1.1.json`? **Recommend:** bump to v1.1 to make the schema delta visible in diffs.
2. **manifest_id collision strategy:** if EnclaveWatch ever computes the same hash for two different exports (vanishingly unlikely with sha256), how do we recover? **Recommend:** include `(vault_id, period_end)` in the hash input.
3. **Should `control_freshness.freshly_observed_implemented[]` accept an empty list?** **Recommend:** yes — empty means "ISSO observed nothing operationally noteworthy this period," which is itself a valid signal that we don't bump freshness for any control.
4. **Per-section signature vs. whole-manifest signature?** **Recommend:** whole-manifest only. Per-section adds complexity for little value when the whole manifest is signed.
